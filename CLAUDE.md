# Coco Cosmetics — Billing System

Internal point-of-sale and inventory management system for a cosmetics retailer in Nicaragua. Handles sales, purchases, cash drawer, employees, clients, and statistics.

## Tech Stack

- **Backend:** PHP 5/7 · CodeIgniter 2 (CI2) + HMVC via `MX` module extension
- **Database:** MySQL (served by XAMPP)
- **Frontend:** Bootstrap 3 · Gentelella admin theme · jQuery · Chart.js · PNotify
- **Printing:** ESC/POS thermal receipt printer via `mike42/escpos-php` (`print/autoload.php`)
- **PDF:** html2pdf (`includes/html2pdf/`)

| Path | Purpose |

**Stage 6 schema (migration `migrations/restaurant_005_bills.sql`):** `bills` (`id_bill`, `id_tab`->`tabs` CASCADE, `label`, `status` open|split|paid|void, `parent_bill` (set on equal-split children), `amount_override` DECIMAL(10,2) (a child's share of the parent subtotal), `id_sale` (set at checkout, Stage 7; no FK), `created_at`) and `order_items.id_bill`->`bills` SET NULL. Every tab gets "Cuenta 1" on open (`Floor_mdl::openTab`); new order lines go to the bill chosen on the order screen or the first open bill; releasing/voiding a tab voids its bills. Controller `Bills` (`/bills/tab/{id_tab}`; create, rename, move_item with partial quantity = line split, merge, split_equal 2..20, undo_split; open to every logged-in user), model `Bills_mdl`. Bill money = subtotal (sum qty*unit_price of active lines) + tip (`tip_rate`% if `tip_enabled`) + IVA (`tax_rate_iva`%), tip/IVA ADDED on top; equal-split children apportion subtotal/tip/IVA with floor-to-cents and the last part takes the remainder so parts add to the parent exactly. A 'split' bill is locked until `undo_split` (refused once any part is paid).

**Stage 7 schema (migration `migrations/restaurant_006_checkout.sql`):** `sales.tip` and `sales.iva` DECIMAL(10,2) (dollars, same unit as product prices; charged ON TOP of the sale lines, `total_invoice = sum(lines) + tip + iva`), `sales.id_bill` (-> `bills.id_bill`, no FK), `bills.stock_deducted`, and an internal service product `products.barcode='SPLIT-CONSUMO'` (hidden from the kitchen menu) that carries an equal-split share as a single sale line. **Checkout from a bill:** `/sales/register?bill=ID` reuses the existing sale form/payment engine in "bill mode" (`Sales::sale_form` builds `$prefill` from `Bills_mdl::checkoutLines()`; `form_sales.php` locks the lines, tip is editable 0..subtotal, IVA fixed, `system.extra_cordobas` is added to the invoice total). On POST `Sales::register` IGNORES the posted lines/prices/discounts and rebuilds them from the bill (`Bills_mdl::checkoutContext`), locks the bill row `FOR UPDATE` inside the transaction, rejects paid/split/empty/changed bills, and `Bills_mdl::settle()` marks the bill paid, links `bills.id_sale`, deducts an equal-split parent's item stock once (on its first paid share), marks the parent paid when all shares are paid, voids empty leftover bills and closes the tab (`tabs.status='paid'`) when nothing is left to collect. Normal bills deduct stock through the normal `Sales_mdl::saveSaleProduct`. Receipts (thermal, PDF, `/sales/details`) print Mesa, Subtotal, IVA and Propina.

## Database Schema (`coco_cosmetics2`)

> Monetary/price values are inconsistently typed: product prices and invoice costs use `VARCHAR`; payment amounts and exchange rates use `DECIMAL`. All PKs are auto-increment integers. FK constraints are enforced at the DB level using `ON DELETE CASCADE` or `ON DELETE SET NULL`. `products` is queried with `WHERE active=1` in the app but the `active` column is absent from the SQL dump — it exists in the live DB. `products.commisssion_rate` has a typo (three s's) that is preserved in the column name.

### App settings

| Table | PK | Key columns | Purpose |

| `settings` | `id_setting` | `setting_key` VARCHAR(100) UNIQUE NOT NULL, `setting_value` VARCHAR(255), `description` VARCHAR(255) | Generic key/value store for app-wide config parameters, intended to grow over time (new settings are new rows, no schema change — `Settings_mdl::save()` only UPDATEs an existing row, so a brand-new key must be seeded with an `INSERT` before it can be edited via `/settings`); admin-editable via `/settings`, gated by `Admin_Controller::is_admin()`. Currently holds `vip_discount_rate` (default `15`) and `birthday_discount_rate` (default `50`) — % discounts auto-filled on service line items in `/sales/register` when the selected client has `clients.is_vip_client=1` or when today's date matches the month/day of `clients.birth_client`, respectively. The birthday discount is additionally gated by `birthday_discount_ceiling_min`/`birthday_discount_ceiling_max` (córdobas, defaults `0`/`999999999` i.e. effectively no cap until an admin tunes real figures) — computed server-side in `Sales::register()` (never trusted from the client, same as the rates themselves): if the sale's total *undiscounted* service line value is below the min, no line is birthday-eligible; otherwise service lines are walked in the order they were added to the sale, accumulating their undiscounted totals, and each is marked birthday-eligible while the running sum stays ≤ the max (both bounds inclusive) — the first line that would push the running sum past the max, and every line after it, is excluded from birthday eligibility. Golden rule (`application/helpers/discount_helper.php`, dependency-free and covered by `application/helpers/tests/discount_helper_test.php`): only one discount effect survives per sale, resolved in two stages. Stage 1, `resolve_single_discount_source()`, picks a single winning source for the whole invoice among category/VIP/birthday — NOT independently per line — by comparing each source's "representative" rate (category's is the highest `service_category.discount_rate` present among the sale's service lines, since category has no single flat rate; VIP/birthday are the flat settings rates above — category/VIP only enter the comparison if they actually apply to ≥1 line, but birthday enters whenever it qualifies for the sale at all (client's birthday today AND undiscounted services total ≥ the ceiling minimum), independent of whether any individual line survived the per-line ceiling walk below, so a single service line whose own amount alone exceeds the ceiling maximum still lets birthday win the sale and fall through to the write-off below rather than silently discounting nothing) and taking the highest (ties broken birthday > VIP > category); the winner is then applied using its own natural per-line rule — category: each line's own rate; VIP: uniform rate on every service line; birthday: its rate only on ceiling-eligible lines — and every other line gets a flat 0, even one with its own category discount. Stage 2, `resolve_coupon_vs_line_discounts()`, then weighs that winning line-discount total in córdobas against a coupon payment on the same sale and neutralizes whichever is smaller (see the `cupon` `sale_payments` rows below). Both stages write `sale_products.discount` (still editable per line after the sale is registered) and are mirrored client-side in `application/views/form_sales.php`'s `recalcBirthdayEligibility()`/`updateTotal()` for on-screen display only — and `company_name` (default `Conceptos`, mandatory/non-empty) — the company name shown in the browser tab title (`header.php`, `form_login.php`) and the opening-cash-drawer email report heading (`open_cash_report.php`); loaded once per request in `Admin_Controller::__construct()` into `$this->header_data['company_name']` for admin pages, and fetched directly by `Login` (extends `MX_Controller`, no `Admin_Controller`) for the pre-auth login page. Also holds 6 receipt-content keys — `receipt_ruc` (default `2811201760006N`), `receipt_address` (default `Costado sur funeraria monte\nlos olivos 2 1/2c al este,\nManagua-Nicaragua.`, multi-line via `\n`), `receipt_phone` (default `8885-1430`), `receipt_tagline` (default `Siente la Diferencia`, stored without quotes — both render sites wrap it in literal `"…"`), `receipt_footer_notice` (default `No se aceptan devoluciones`), and `receipt_footer_thanks` (default `Gracias por preferirnos!!\nLe esperamos pronto.`, multi-line via `\n`) — the store info printed on the header/footer of every sale receipt, previously hardcoded in `Sales.php`; consumed by both `Sales::printInvoice()` (ESC/POS thermal print) and `Sales::generateReceiptPdf()` (archived PDF copy, `receipt_address`/`receipt_footer_thanks` rendered via `nl2br()`), editable via `/settings`. Also holds 4 dynamic-logo keys — `logo_header`, `logo_login`, `logo_receipt`, `logo_purchase_order` (all default `NULL`) — each storing the generated filename (32-char hex + original extension, e.g. `a1b2...c3.png`) of an admin-uploaded replacement for one of the 4 previously-hardcoded `assets/img/` logos; physical files live in `uploads/logos/` (gitignored). `Settings::uploadLogo()` validates (extension whitelist png/jpg/jpeg, `getimagesize()` real-image check, 5MB max), re-encodes via GD (`Settings::compressLogoImage()` — downscales past 1000px and re-saves at `imagepng` level 9 / `imagejpeg` quality 85, both visually lossless) into a freshly hashed filename, updates the `setting_value` only after the new file is confirmed on disk, and only then deletes the previous custom file (rollback-safe: a DB-save failure after upload deletes the just-written file and leaves the old value/file untouched). `resolveLogoUrl()`/`resolveLogoPath()` (`misc_helper.php`) resolve each key to either the custom `uploads/logos/` file (if set and still present on disk) or the original bundled `assets/img/` file, which is never deleted and acts as the permanent fallback — consumed via `resolveLogoUrl()` in `header.php`/`form_login.php` (browser `<img>`) and `resolveLogoPath()` in `Sales.php`'s thermal-receipt printing and `Orders.php`'s purchase-order PDF generation (server-side file paths) |
